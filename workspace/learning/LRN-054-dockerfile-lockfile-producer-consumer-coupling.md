## What happened

The template Dockerfile (GH-70d) planned a `COPY uv.lock ./` instruction, but no scaffold skill generates or commits a `uv.lock` at project creation time, and no `uv.lock` exists in the template tree. Additionally, uv is never installed in the build stage and the bare `pip install` lines were never replaced with `uv sync --frozen`. Every `docker build` of a freshly scaffolded agent would fail on the missing-file COPY.

## Root cause

The four GH-70 todos (a–d) were labelled parallel-independent. In fact GH-70b/c (lockfile generation at scaffold time) must precede GH-70d (lockfile consumption in Dockerfile). Treating lockfile-producer and lockfile-consumer changes as independent allows the consumer to land without a producer, producing a broken template.

## Check

```bash
# If a template Dockerfile contains a uv lockfile COPY, a uv.lock must exist
# in the scaffold output or be generated by a scaffold skill:
grep -n "COPY uv.lock" template/Dockerfile 2>/dev/null && \
  ls template/uv.lock 2>/dev/null || echo "lockfile-consumer without producer"

# Also verify uv is installed in the build stage before uv sync is called:
grep -n "uv" template/Dockerfile | head -20
```

## Prevention

When planning any wave that adds a `COPY <lockfile>` to a Dockerfile, treat the lockfile-generator todo (scaffold skill or CI step that produces the file) as a hard prerequisite in the same wave, not a parallel peer. Mark the group as dependency-ordered in the wave header. Never close the consumer todo until the producer todo is also closed and the lockfile can be found at the COPY source path.
