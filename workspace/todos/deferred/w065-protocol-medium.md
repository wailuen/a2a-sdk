# w065 protocol-audit mediums/lows (deferred, 2026-10-24)

No critical/high from any advisor.

- [AG-UI/medium] agent_sdk/routes/ag_ui.py:415-431 builds AGENT_ARTIFACT with data = payload.wire(). For the prose content type, wire() returns a bare markdown string (agent_sdk/models/content_types.py:1024, GH-179). The agent card (agent_sdk/routes/agent_card.py, AGENT_ARTIFACT valueSchema) declares data as type object. A consumer that validates against the card will reject or drop prose artifacts. Conformance verdict for ag_ui.py overall: PASS (RUN_STARTED first at :729, exactly one terminal on every path incl. exception/cancel/unserializable-frame, camelCase bare data: frames via sse_data, all 5 CUSTOM names match the card list and console routing); this is the only contract mismatch found. Fix: Change the AGENT_ARTIFACT valueSchema data to oneOf [object, string] (or drop the type constraint), and document that prose artifacts carry a markdown string.

- [AG-UI/low] agent_sdk/routes/ag_ui.py reads only threadId, runId, state, messages, resume and forwardedProps (a2uiClientCapabilities, timezone). RunAgentInput.tools (frontend tools, the basis of Static GenUI) and RunAgentInput.context are never read, and nothing tells the client they were dropped. Messages with role tool/system/developer are also dropped in _fold_history (ag_ui.py:131). A frontend that relies on client-defined tools gets no tool calls and no error. Fix: Document in docs/protocols.md that tools/context/non-user-assistant roles are ignored by design, or reject/echo a CUSTOM warning when tools is non-empty.

- [AG-UI/low] agent_sdk/routes/ag_ui.py:556-558 and :757-761 accept a resume entry with no status (status is None passes) and deliver {status: None} to deliver_resume. The spec requires status in {resolved, cancelled}. Values that are present are validated correctly. Resume entries also accept snake_case interrupt_id as well as interruptId (:559), which is lenient but harmless. Fix: Treat a missing status as invalid resume entry, or document the default (resolved) explicitly.

- [AG-UI/low] agent_sdk/routes/ag_ui.py:670-673 replaces a missing, empty or non-string threadId/runId with a fresh uuid, and only camelCase keys are read. A client sending thread_id gets a new thread on every call, so conversation continuity (context_reusable_messages keyed by thread) breaks with no error. Documented design (GH-97), but silent. Fix: Optionally log or reject when thread_id/run_id snake_case keys are present and the camelCase keys are absent.

- [AG-UI/low] agent_sdk/routes/agent_card.py:160 advertises the AG-UI extension as https://agent-sdk.dev/extensions/ag-ui-run/v1, not urn:agui:run:v1, alongside an x-agui block. The endpoint is declared in both (trap 14 is satisfied) and customEvents names match the emitter. A consumer that only detects urn:agui:run:v1 will skip the extension form but still find x-agui. Acceptable per the rule, but consumers must accept both. Fix: Either also declare urn:agui:run:v1 or document in docs/protocols.md that detection is via x-agui or the agent-sdk.dev URI.

- [AG-UI/low] agent_sdk/routes/ag_ui.py:677-700 (_emit) serializes frame by frame. A TextEvent maps to START/CONTENT/END in one batch (:332-336). If CONTENT cannot be encoded (e.g. a lone surrogate in event.text), START is already written, CONTENT and END are dropped, and RUN_ERROR follows, leaving a TEXT_MESSAGE_START with no END. RUN_ERROR is terminal so most clients tolerate it, but a strict client may flag the dangling message. Rare path. Fix: Pre-validate the batch (serialize all frames first, then write), so a failing batch emits only RUN_ERROR.

- [A2UI/medium] agent_sdk/a2ui/catalog.py:240 (_COMPACT_SCHEMAS TimeSeriesChart) teaches x_key and y_key as free strings ("x_key":str,"y_key":str). The model in models/content_types.py:772-776 lets x_key/y_key be any string, but TimeSeriesDataPoint (content_types.py:730) can only carry date, value and label. I confirmed it: TimeSeriesChart(x_key="month", y_key="price", data=[TimeSeriesDataPoint(date=..., value=1.0)]).wire() gives x_key "month" while the points hold only date/value. A spec renderer that reads point[x_key] gets undefined, which shows as a blank axis or NaN. The console renderer (a2ui.js) never reads x_key or y_key, so the bug is hidden locally. Fix: In the compact schema, show the only valid values: "x_key":"date","y_key":"value". Also add a validator on TimeSeriesChart that rejects any x_key other than "date" or y_key other than "value", or that remaps the data points.

- [A2UI/low] Some compact schemas teach fields that are not in the frozen Profile contract. EntityList at catalog.py:243 adds title? and showing?. The models also emit extras the compact schemas leave out: ComparisonTable sort_by/sort_order and ColumnDef unit/highlight/is_id, CalendarEvent is_online, DocumentItem web_url/last_modified/modified_by. Profile v1.1 does not list any of these. They are harmless only if every receiver ignores unknown fields, and the Profile says only that metadata must be tolerated. A strict v1 renderer could reject them. All required and optional marks that the compact schemas do show match the Profile (checked for all 14 frozen types). The only difference is that the compact schemas make model-defaulted fields required, as the Profile does. Fix: Either drop title? and showing? from the EntityList compact schema, or record them in DESIGN.md as SDK extensions that receivers must ignore. Do the same for the other extra fields.

- [A2UI/low] A2uiCapabilities.from_metadata (translator.py:85-112) reads tier and catalogs but ignores the client's version field. A client that advertises v0.8 still gets v0.9.1 messages (createSurface/updateComponents with the component-property discriminator), which a v0.8 renderer cannot read. The Profile gives the emitter a duty to check tier and catalogs, not version, so this is not a violation. It is a gap in graceful degradation. Fix: Keep the field from the client. When it is present and is not v0.9 or v0.9.1, treat the client as not capable (return None from translate so the TextPart fallback is used), or log once. Or write down the decision to always send v0.9.1.

- [A2UI/low] _annotation_str (catalog.py:66-106) prints dict-typed fields as plain 'dict'. Real output: MultiCategoryPeriod{categories: dict} and MultiCategorySummary{by_category: dict}, so the {name: {value, count?}} shape is lost. Domain cards with dict fields get a less accurate prompt line. Enum-valued fields such as presence.availability in the UserProfile compact schema are shown as 'str' with no value list, while show_as is shown with its values. The built-in types are not affected because they use hand-written compact schemas. Fix: Render dict[K, V] as {key: V-shape}. Use the Literal or enum value list in the UserProfile/UserList presence compact schemas.

- [A2UI/low] supported_catalogs(emits=None) (catalog.py:357-362) always lists the Standard Profile catalog, even when allowed_components removes every Standard type. The only production caller (routes/agent_card.py:156) always passes emits, so this is latent. Also, emits is typed Iterable[type] but is walked twice in the card builder (once in supported_catalogs, once in a2ui_extension). A generator would be used up on the first pass and the advertised list would be empty. Today a list is passed. Fix: In the emits=None branch, add CATALOG_ID only if a Standard type passes the allowed_components filter. Change the emits parameter to Sequence, or call list(emits) once at the top of each function.

- [A2UI/low] SurfaceRegistry.open (translator.py:263-273) warns and ignores a duplicate createSurface. The spec calls that an error (delete first, then recreate). apply_data_model_update (translator.py:282-455) treats numeric tokens as dict keys, so it cannot apply an array path such as /metrics/0 as the spec and the renderer do. It also rejects '..' tokens that the renderer accepts as keys. translate() never reaches any of this, and GH-249 marks both helpers INTERNAL and out of __all__. They are also not called anywhere in agent_sdk. Whole-model replace with value=model would clear the data before copying it. Every divergence is written down in the docstrings and covered by tests. I am recording these for the record, not as defects to fix. Fix: No code change needed now. If these helpers ever become public, make a duplicate createSurface raise, add list-index support, and guard against value being the same object as model.

- [SEAM/medium] agent_sdk/routes/agent_card.py build_agent_card() now leaves the A2UI extension off the card when no tool emits an A2UI type (GH-249), but still always lists "application/a2ui+json" in defaultOutputModes. The card offers A2UI output while it does not offer the A2UI extension. A client that reads only defaultOutputModes will expect A2UI parts that can never come. tests/test_gh249_a2ui_gating.py::test_empty_catalog_card_has_no_a2ui_extension checks only the extensions list. Fix: In build_agent_card(), add "application/a2ui+json" to defaultOutputModes only when supported_catalogs(allowed_components, emits) is not empty (the same condition that adds the A2UI extension). Extend the GH-249 test to check that defaultOutputModes has no a2ui+json when the catalog is empty.

- [SEAM/medium] agent_sdk/routes/a2a.py _echo_extensions() echoes any requested URI found in _ECHO_EXTENSION_URIS = {A2UI_EXTENSION_URI, CREDENTIAL_FORWARDING_EXTENSION_URI}. It never checks the card. (1) With an empty A2UI catalog the card has no A2UI extension (GH-249), yet message:send / message:stream / :subscribe still answer 'X-A2A-Extensions: https://a2ui.org/a2a-extension/a2ui/v0.9.1' when the client asks, and _capabilities() still opts the client in. (2) The credential-forwarding URI is echoed as active even when credential_forwarding_extension() returned None and the card does not list it. The response claims an extension is active that the card says does not exist. Fix: Build the activatable set from the extension URIs on app.state.agent_card (intersect with _ECHO_EXTENSION_URIS / _STREAM_ONLY_EXTENSION_URIS). Pass opted_in=False to A2uiCapabilities.gated() in a2a._capabilities() when the card has no A2UI extension. Add a test: empty-catalog app + A2UI header -> no echo; no credential sources + forwarding header -> no echo.

- [SEAM/low] agent_sdk/console/static/chat.js sendA2a() always sends the hard-coded header 'X-A2A-Extensions: https://a2ui.org/a2a-extension/a2ui/v0.9.1' plus metadata.a2uiClientCapabilities, even when loadCatalogIds() found no A2UI extension on the card. The console opts into an extension the server says it does not offer, and this hides the server-side echo issue above during console and acceptance runs. Fix: In loadCatalogIds(), record whether the A2UI extension was found and use its uri; in sendA2a(), send the header and the metadata only when it was found, using the card's URI instead of the literal.

- [SEAM/low] MCP and A2A protocol versions are typed out by hand in several places that do not agree. agent_sdk/routes/admin.py selfcheck_info() hard-codes "a2a_protocol_version": "0.3.0" and "mcp_protocol_version": "2025-06-18". agent_sdk/console/static/mcp.js hard-codes MCP_PROTOCOL_VERSION = "2025-06-18". agent_sdk/testing/mcp.py uses SUPPORTED_PROTOCOL_VERSIONS[0] (= 2025-11-25). Because serverInfo.title is gated at 2025-11-25 in routes/mcp.py _handle_initialize(), the Python test client always gets title and the console self-check never does. Neither path covers both versions, and a future change to SUPPORTED_PROTOCOL_VERSIONS or the AgentCard protocolVersion default will not reach admin.py or mcp.js. Fix: In admin.py, take mcp_protocol_version from routes.mcp.SUPPORTED_PROTOCOL_VERSIONS (or state on purpose that the console pins 2025-06-18 to copy Claude.ai). Take a2a_protocol_version from the AgentCard model default or from app.state.agent_card['protocolVersion']. Have mcp.js read the version from selfcheck-info instead of its own constant. Add one test that initializes at both 2025-06-18 and 2025-11-25 and checks the title gate.

- [SEAM/low] All four surfaces now use common/body.py read_capped_body(), but they react to an over-cap body differently. AG-UI (ag_ui.py:642), MCP (mcp.py:1130, 1528) and OAuth (oauth.py:331) return HTTP 413. A2A _parse_send (a2a.py:471) returns a2a_invalid_params, which is HTTP 400 with -32602. The caps also differ: A2A 1 MB, AG-UI 1 MB, MCP 2 MB, OAuth 16 KB. The AG-UI comment at ag_ui.py:85 says its cap 'mirrors MCP/OAuth caps', which is not true. Fix: Either map A2A over-cap to HTTP 413 (keep a JSON-RPC style error body, for example -32602 with status 413 via a headers/status override in a2a_error), or write down the 400 choice in docs/protocols.md. Correct the ag_ui.py:85 comment so it names the real MCP (2 MB) and OAuth (16 KB) caps.

- [A2A/medium] TaskStatus always carries a non-spec `error` field on failed tasks (agent_sdk/models/a2a.py:116). The card declares it as extension https://agent-sdk.dev/extensions/task-error/v1 (agent_sdk/routes/agent_card.py:114-128), but the field is not gated on that URI appearing in X-A2A-Extensions, and the key is not x- namespaced. Every client gets it, including ones that never asked. A strict validator against a2a.json would flag it. Fix: Emit status.error only when the request activated the task-error URI (and echo it in X-A2A-Extensions), or move the detail into status.message.parts / status.message.metadata (or an x- prefixed key).

- [A2A/medium] acceptedOutputModes is only used as a yes/no gate that returns -32005 when nothing matches (agent_sdk/routes/a2a.py:452-457). It never shapes the output. A client sending ["text/plain"] still gets application/json DataParts, and A2UI DataParts are decided only by the X-A2A-Extensions header (a2a.py:429-438). The spec meaning is 'the MIME types this client accepts'. Fix: Thread the accepted modes into artifact building. Drop DataParts (keep the TextPart fallback) when neither application/json nor application/a2ui+json is accepted. Or document the deviation on the card.

- [A2A/low] Since GH-249 the A2UI extension is left off the card when there is no catalog (agent_sdk/routes/agent_card.py:156-157), but defaultOutputModes still lists application/a2ui+json (line 191), and message:send still accepts it as an output mode (a2a.py:151). The card advertises an output type the agent cannot produce in that configuration. Fix: Build defaultOutputModes from the same supported_catalogs() check: add application/a2ui+json only when the A2UI extension is on the card.

- [A2A/low] GET /v1/tasks (agent_sdk/routes/a2a.py:1053-1075) returns the right envelope (tasks, totalSize, pageSize, nextPageToken). It silently ignores any filter query params (contextId, status, historyLength, etc.) and silently clamps pageSize<=0 or >100 instead of returning -32602. A client that filters by status or contextId gets an unfiltered list and cannot tell. Fix: Support at least contextId and status filters, and historyLength. Return -32602 for out-of-range pageSize, or document the clamp.

- [A2A/low] message/send or message/stream with a taskId for a task that is non-terminal but not interrupted (working or submitted) returns -32004 'task is not awaiting input' (agent_sdk/routes/a2a.py:578-580). The spec lets a client send a follow-up to any non-terminal task. The terminal-task rejection (a2a.py:570-577) is correct. Fix: Document this as an intentional limit on the card or in docs/protocols.md, or queue the message for the running worker.

- [A2A/low] For A2UI artifacts the DataPart metadata holds only mimeType, and for plain scalars only mimeType=application/json (agent_sdk/agent/runner.py:444-449, 471-475). data_type and tool_name sit only on Artifact.metadata. A consumer that reads the hint from the DataPart (as the spec rule says) finds nothing. Separately, a declared-emits tool whose result matches no declared type yields a TextPart-only artifact (runner.py:388-402, GH-225), which is a text-only structured result by design. Fix: Copy data_type and tool_name into every DataPart.metadata, as the raw-dump branch already does. Keep the GH-225 text-only case documented as a deliberate ruling.

- [A2A/low] 401s from require_identity and /oauth/revoke send `WWW-Authenticate: Bearer resource_metadata="..."` for both a missing token and a bad token (agent_sdk/auth/middleware.py _unauthorized/_prm_challenge, agent_sdk/routes/oauth.py:1185-1189, 1198-1202). A presented-but-invalid token gets no error="invalid_token", so a client cannot tell 'no token' from 'bad or expired token' and may not refresh. Fix: Add error="invalid_token" to the challenge when a token was presented and rejected; leave it off when no token was sent.

- [A2A/low] The shared unauth_rate_limit dependency raises HTTPException(429), so /oauth/register, /oauth/token and /oauth/revoke answer a rate-limit with FastAPI's bare {"detail": ...} rather than the RFC 6749/7591 error object their other failures use (agent_sdk/routes/oauth.py:334, 1086, 1154; the handler wrapping is /v1 only). Also, the requested `scope` is stored and echoed in the token response unvalidated (oauth.py:612, 1002) even though the AS metadata (scopes_supported: []) and the card (scopes: {}) advertise none. Fix: Catch the rate limit on the OAuth routes and return {error: temporarily_unavailable} with Retry-After. Either drop unknown scopes or reject them with invalid_scope.

- [MCP/medium] One per-IP limiter (default 30/min, AGENT_SDK_UNAUTH_RATE_LIMIT) guards the bearer-less 401 challenge on /mcp (auth/middleware.py:120-121), POST /oauth/register (oauth.py:334), GET and POST /oauth/authorize (oauth.py:658, 922), POST /oauth/token (oauth.py:1086) and POST /oauth/revoke (oauth.py:1154). Claude.ai makes the register, token and refresh calls from its own servers, so many users probably share a few source addresses. Past the limit the server answers 429 where Claude.ai expects the 401 challenge or a token. That shows up as 'Couldn't connect' or 'Authorization failed'. Found by reading the code. I did not load-test it. Fix: Raise the default to several hundred per minute. Or give /oauth/token and /oauth/register their own bucket keyed on client_id plus IP. Never let the bearer-less 401 on /mcp turn into a 429. Return the 401 with the challenge header and rate-limit only repeated bad credentials.

- [MCP/low] SUPPORTED_PROTOCOL_VERSIONS includes 2025-03-26 (mcp.py:148). tools/list always adds tool title and outputSchema (mcp.py:771-775). tools/call always adds structuredContent (mcp.py:1065-1078). All three were introduced in 2025-06-18, so a client that negotiated 2025-03-26 gets fields its schema does not define. _dispatch is version-blind. The comment at mcp.py:578-581 says this is deliberate (GH-246). The only version gate is serverInfo.title, so the gating policy is inconsistent. In practice Claude.ai negotiates 2025-06-18 or later, so impact is low. Fix: Either pass the negotiated version into _dispatch and drop title, outputSchema and structuredContent for 2025-03-26 sessions, or drop 2025-03-26 from the negotiable set and keep it only as the absent-header assumption. If neither, record it as a known deviation in DESIGN section 5.5.

- [MCP/low] Verified in _handle_initialize (mcp.py:582-586). title appears only when the negotiated version is 2025-11-25 and is absent at 2025-06-18 and 2025-03-26. SUPPORTED_PROTOCOL_VERSIONS is newest-first with an import-time assert (mcp.py:151-153). initialize echoes a supported client version and otherwise returns 2025-11-25 (mcp.py:562-567). icons is never emitted, which is correct. Per mcp-protocol.md section 14, title is valid from 2025-06-18, so omitting it at 2025-06-18 is spec-valid but is not required. The gate rests on a GH-43 observation that was never re-tested. Fix: Keep the gate. The audit brief expects it. Re-test against live Claude.ai at 2025-06-18 and either lower the gate or write the result into REVIEWS.md so the question closes.

- [MCP/low] The registry only seeds readOnlyHint and destructiveHint=false when read_only=True (agent/registry.py:532-535). Otherwise it adds only openWorldHint (registry.py:643-644). tools/list passes that dict through unchanged (mcp.py:776-777). Per spec, destructiveHint defaults to true and idempotentHint to false. Every non-read-only tool is therefore advertised as destructive unless the author sets annotations by hand. Directory submission wants explicit hints. Claude.ai will ask for approval on these tools. Fix: Warn at registration when a non-read-only tool sets neither destructiveHint nor idempotentHint. Document the override in docs/tools.md.

- [MCP/low] /oauth/token never reads form['resource'] (oauth.py:1086-1129). The audience bound at authorize does travel through the code, the access token and the refresh rotation, and verify() checks it (auth/oauth_tokens.py:566-580). So the issue, persist and check-at-use chain is real. But MCP 2025-06-18 clients must send resource on the token request, and a wrong value is accepted silently instead of returning invalid_target. The module docstring says it is skipped because Claude.ai omits it. Fix: If resource is present on the token request, run store.validate_audience on it and require it to equal the code's or refresh record's audience. Otherwise return invalid_target. Keep accepting its absence.

- [MCP/low] accepted_audiences is {issuer, issuer/mcp} and verify() has no surface context (auth/oauth_tokens.py:139, 577). The PRM advertises different resources: issuer/mcp for /mcp (oauth.py:171-177) and the bare origin for A2A and AG-UI (oauth.py:180-186). A token minted for issuer/mcp is therefore also accepted on /v1/* and /ag-ui/*, and the reverse. Both are the same server, so exposure is small, and the code documents it as a deliberate ruling. Under a strict reading of RFC 8707 and MCP section 11, a token bound to one resource should not work at another. Fix: Optional hardening: pass the expected audience into verify() per route group, with MCP expecting issuer/mcp and A2A/AG-UI expecting the bare origin. Accept the other value only for the Claude.ai bare-origin quirk on /mcp.

- [MCP/low] In rotate_refresh (auth/oauth_tokens.py:429-470) the stored client_id is compared only at the end. Before that, a rotated, expired or require_user-failing record already triggers revoke_family or delete. A different public client that holds a victim's stale refresh token can burn that family or record before the mismatch is rejected. The attacker needs the token already. Reuse detection is a defensible reason to revoke anyway. Fix: Move the client_id equality check to right after the record loads. Decide on purpose whether a mismatched client presenting a rotated token should still revoke the family, and write that down.

- [MCP/low] auth/middleware.py:78-90 sends the same challenge for a missing token and for an invalid or expired one: Bearer resource_metadata="...". There is no error="invalid_token" and no scope parameter. This works with Claude.ai, because any 401 restarts discovery. The same shape is reused at oauth.py:958, 1188 and 1201. Fix: Add error="invalid_token" when a token was presented and failed. Consider adding scope when scopes_supported is non-empty.

- [MCP/low] mcp_get sends a padding comment and then bare heartbeat frames, with no id: or retry: field (mcp.py:1343-1353). A client cannot resume. This is harmless today, since the server sends no server-initiated messages and listChanged is false, and the code states it. At capacity the route returns 429 instead of 405 or the stream. That is a documented deviation (RT-003), but mcp-claude-platforms P8 lists 429 on this path as a known Couldn't-connect cause. Fix: No change needed now. If server-initiated messages are ever added, send an id-only priming event and implement Last-Event-ID replay on the same stream. Keep the per-identity cap well above the org size.

- [MCP/low] The PRM omits scopes_supported (oauth.py:171-186). The AS metadata advertises scopes_supported as an empty list and omits revocation_endpoint_auth_methods_supported (oauth.py:200-219). It does not advertise Client ID Metadata Document support. Under 2025-11-25 clients try pre-registered, then CIMD, then DCR. DCR is advertised, so Claude.ai connects. The required items are all present: S256, registration_endpoint, issuer, response_types_supported, and a PRM resource that matches the /mcp and bare URLs. Fix: Optional: drop the empty scopes_supported or fill it in, add revocation_endpoint_auth_methods_supported, and plan CIMD for 2025-11-25-first clients.
