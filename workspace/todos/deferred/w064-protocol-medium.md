# w064 protocol-audit mediums (deferred, 2026-10-24)

No critical/high. Mediums below from the w064 protocol audit, kept for a later wave.

- [MCP/medium] agent_sdk/routes/mcp.py:1066-1070 (mcp_post) and :1461-1464 (mcp_messages) call `await request.body()` and only then compare `len(raw)` to `_MAX_BODY_BYTES` (2 MiB). The whole body is buffered before the 413. There is no Content-Length pre-check here and no ASGI body-limit middleware elsewhere in agent_sdk (grep found only a Content-Length check in contrib/webhooks/graph.py). Any authenticated caller can make the server buffer a very large body per request. Auth runs first (Depends(require_identity)), so this is not anonymous.

- [MCP/low] agent_sdk/routes/mcp.py:1160 (`if response is None or message.get('id') is None: return 202`). `_dispatch` only treats `notifications/*` methods as notifications. A `tools/call` with no id (or id:null) is therefore fully executed, including any side effects, and the result is silently dropped with a 202. MCP requires request ids to be string or integer and non-null. The same path exists in mcp_messages at :1507.

- [MCP/low] agent_sdk/routes/mcp.py:693-743 (`_handle_tools_list`) is not version-aware. It always emits tool `title` and `outputSchema`, and tools/call always emits `structuredContent`. These arrived in 2025-06-18, yet 2025-03-26 is in SUPPORTED_PROTOCOL_VERSIONS (:141), so a 2025-03-26 session receives version-future fields. serverInfo.title gating at :538-547 is done correctly (title only when the negotiated version is 2025-11-25 or newer, absent at 2025-06-18), so this is an inconsistency of approach, not a handshake break. Claude.ai negotiates newer versions, so impact is limited to old or strict clients.

- [MCP/low] Comments in agent_sdk/routes/mcp.py contradict each other on serverInfo.title. Lines 148-153 say the spec introduced title in 2025-06-18 and the SDK gates it at 2025-11-25 because of GH-43. The comment at :539-540 says 'title was added in 2025-11-25'. The reference digest (mcp-protocol.md line 64) says title was added in 2025-06-18. The behaviour (present at 2025-11-25 and later, absent at 2025-06-18 and 2025-03-26) matches the audit rule and is spec-valid, since title is optional. Only the comment at :539 is wrong, and the GH-43 rationale is still unverified live.

- [MCP/low] agent_sdk/routes/mcp.py:1439-1514 (legacy POST /mcp/messages) differs from mcp_post. It has no Content-Type check, so no 415 for non-JSON bodies (mcp_post does at :1056-1062). It has no `_is_jsonrpc_response` branch, so a client reply that carries id and result is dispatched as a method-less request and an -32600 error is enqueued instead of being acknowledged. On a full queue it returns a bare-bytes 503 instead of a JSON body. This is the back-compat transport only and Claude.ai uses Streamable HTTP, so impact is low.

- [AG-UI/medium] agent_sdk/routes/ag_ui.py:714-745. The resume entry is forwarded to the paused tool as {"status": entry.get("status"), "payload": entry.get("payload")} with no check on status. A missing status, or any value outside the spec enum (resolved/cancelled), reaches the tool's resume_handler unchanged. Only the entry count (len>1) and dict shape are checked. Interrupt id lookup (find_interrupt) and the 'unknown or expired interrupt' path are correct and identity-bound. The route also reads interruptId OR interrupt_id (_resume_interrupt_id, line 525); camelCase is the spec form and the snake_case fallback is a deliberate tolerance (comment at 721).

- [AG-UI/low] agent_sdk/routes/ag_ui.py:351-365. On a resume run the mapper injects a synthetic TOOL_CALL_START / TOOL_CALL_ARGS(delta "{}") / TOOL_CALL_END for a toolCallId that the client already received in the previous (interrupted) run with the real arguments. Within the run the sequence is valid (START, ARGS, END, then RESULT). Across the thread, a client that keeps one message list sees the same toolCallId twice, the second time with empty args and no parentMessageId (last_message_id is None on a fresh mapper), so it may append a duplicate tool call on a new assistant message or overwrite the real args. This is a documented SDK choice (DESIGN.md 5.3), so it is not a spec violation, but it trades correctness of client state for compatibility with strict per-run verifiers.

- [AG-UI/low] agent_sdk/routes/ag_ui.py:597-760. The route reads only threadId, runId, state, messages, resume and forwardedProps (a2uiClientCapabilities, timezone). RunAgentInput.tools (frontend tools) and RunAgentInput.context are never read, and parentRunId is neither read nor echoed. Static GenUI (frontend tool bound to a component) therefore cannot work against this endpoint. Declarative GenUI via the A2UI_UPDATE CUSTOM event does work. Absent tools/context/forwardedProps are accepted without error. This is a capability gap, not a wire violation.

- [AG-UI/low] agent_sdk/routes/ag_ui.py:633-638. A missing or non-string threadId/runId is replaced with uuid4().hex instead of being rejected, so RUN_STARTED and RUN_FINISHED carry ids the client never sent. This is deliberate (GH-97, docstring at 210-214) and keeps RUN_STARTED first. A client that omits the ids cannot correlate the run, and a non-string id is silently replaced. A malformed body also yields HTTP 200 plus RUN_ERROR rather than 4xx, which is consistent with the RUN_STARTED-first rule.

- [AG-UI/low] agent_sdk/routes/ag_ui.py:642-665 and 694-696. If serializing the RUN_STARTED frame ever failed, _emit's except path would emit a RUN_ERROR as the first and only frame, with no RUN_STARTED, which breaks the first-event rule. The code comment (690-693) says this cannot happen today because threadId/runId come from loads_strict or uuid4, so this is a latent defect only. Everything else checked is conformant: bare 'data: <json>' frames, camelCase keys on every frame, exactly one terminal RUN_FINISHED or RUN_ERROR on every exit path (including the final 'stream ended unexpectedly' fallback), STATE_SNAPSHOT second, TEXT_MESSAGE_START/CONTENT/END sharing one non-empty messageId, TOOL_CALL_START/ARGS/END/RESULT ordering, RUN_FINISHED.outcome success|interrupt with camelCase responseSchema/toolCallId/expiresAt, and the five CUSTOM names (A2UI_UPDATE, AGENT_ARTIFACT, AGENT_PROGRESS, AGENT_NOTE, TOOL_PROGRESS) documented in docs/protocols.md and the agent card x-agui block with an explicit endpoint.

- [SEAM/medium] agent_sdk/routes/mcp.py _handle_initialize keeps serverInfo.title back unless the agreed MCP version is 2025-11-25. The stated reason is GH-43: Claude.ai rejected a 2025-06-18 handshake that had a title. But _handle_tools_list (around line 730) adds tool.title for every registry tool at every version, including 2025-03-26, which has no title field. This wave also adds a fixed "title": "Load skill" to the load_skill tool (_load_skill_tool), so every agent in mcp_skills="tool" mode now sends a title at every version. outputSchema (a 2025-06-18 field) is also sent to 2025-03-26 sessions. DESIGN.md line 380 says tools/list output does not change with the version, and also ends with "version-future fields gated on the negotiated version". Those two statements disagree, and only the initialize step follows the second.

- [SEAM/low] agent_sdk/testing/mcp.py line 36 hard-codes PROTOCOL_VERSION = "2025-11-25". The module already imports from ..routes.mcp, but it does not use SUPPORTED_PROTOCOL_VERSIONS[0]. If the server adds a newer version or drops this one, the test client will drift without notice. The client also never sends the MCP-Protocol-Version header after initialize, though spec section 10 says a client MUST. So the acceptance client only tests the server's fallback for a missing header (GH-200), never the normal path where the header is present.

- [SEAM/low] agent_sdk/routes/mcp.py contradicts itself about when serverInfo.title arrived. The comment at line 148 and the _handle_initialize docstring say 2025-06-18, gated at 2025-11-25 to be safe. The comment just above the gate (around line 540) says "title was added in 2025-11-25", which is wrong.

- [A2UI/medium] agent_sdk/a2ui/catalog.py:318-348 (supported_catalogs) and :361-399 (a2ui_extension). When the registered tools declare no A2UI-emitting types, supported_catalogs(None, []) returns []. agent_sdk/routes/agent_card.py:153-157 still adds the A2UI extension to the card every time. Checked live: a2ui_extension(None, []).params is {'supportedCatalogIds': [], 'acceptsInlineCatalogs': False, 'dataEncoding': 'data.messages'}. The card then says it speaks A2UI but names no catalog, so a client that matches catalog ids against the card finds nothing in common.

- [A2UI/low] agent_sdk/a2ui/translator.py:127-130 (A2uiCapabilities.extended) uses the test 'extended' in self.tier. Checked live: from_metadata({'tier':'non-extended'}).extended is True. The Profile defines only 'core' and 'core+extended', and a client that sends an unknown tier should be treated as the safe default, 'core'. A substring match can turn on Extended types for a client that did not ask for them. Impact is small because Extended types still fall back to prose on a client that cannot render them.

- [A2UI/low] agent_sdk/a2ui/catalog.py:104-179 (_field_summary), used only for custom types that have no _COMPACT_SCHEMAS entry. It decides required-ness from FieldInfo.is_required(). A field with a default that is always written to the wire, such as TimeSeriesChart.x_key, y_key and total_count, shows as 'x_key?' there. _COMPACT_SCHEMAS shows the same fields as required, which matches Profile v1.1. It also prints nested models only by class name (for example '[BarItem]', 'ManagerRef|null'), so the model is never told the inner field names. All 14 built-in types use _COMPACT_SCHEMAS, and I checked them: every '?' in them marks a field that is optional in the Profile and in the model, so this affects custom types only.

- [A2UI/low] agent_sdk/a2ui/catalog.py:211-238. Some optional Profile fields are not in the compact strings: TimeSeriesChart x_label, y_label and summary; MultiCategoryChart chart_config; UserProfile presence.status_message and the out_of_office sub-fields other than is_enabled; ComparisonTable sort_by and sort_order (SDK extensions). The header at lines 269-270 says 'required fields shown, ? = optional', which reads as 'every optional field is listed too'. No required field is missing and no '?' is on a required field. The 14 types match the Profile tiers: Core 7 (6 frozen plus reserved TradeActivity, which is correctly not registered) and Extended 8 frozen, with the reserved ones also not registered.

- [A2UI/low] agent_sdk/a2ui/translator.py:245-272 (SurfaceRegistry) and :275-445 (apply_data_model_update). Nothing under agent_sdk/ imports either one, so they are not used by production code. translate() only writes the flat '/root' pointer. As written, apply_data_model_update treats numeric tokens as dict keys and raises on a list in the path. The spec's own pointers such as '/items/0/name' therefore cannot be applied. The docstring records this as a deliberate divergence from the renderer's pointerSet. SurfaceRegistry.open warns and ignores a duplicate createSurface instead of raising; the spec calls that a protocol error. This is latent, but a third-party user of these helpers would hit it.

- [A2A/medium] agent_sdk/routes/a2a.py:1219 serves only POST /v1/tasks/{id}:subscribe. That matches the v0.3.0 spec prose (specification.md section 7.9 and the repo digest .claude/reference/a2a-protocol-0_3_0.md:67, LRN-099). But specification/grpc/a2a.proto at the v0.3.0 tag maps TaskSubscription to `get: "/v1/{name=tasks/*}:subscribe"`. A client generated from the proto, or the reference a2a-python/a2a-js REST clients, will send GET and get 405 (code -32004). The spec contradicts itself here, so the SDK is defensible but not interoperable with proto-derived clients. All other REST verbs checked match both sources.

- [A2A/medium] message_send returns a bare Task or Message (a2a.py:662,679,700). message_stream and tasks_resubscribe emit bare Task/status-update/artifact-update objects (a2a.py:910,917,940). The v0.3.0 spec REST section 7.1 says the response is `{message?, task?}`. Section 7.2 and 7.9 say stream frames are `{message?, task?, statusUpdate?, artifactUpdate?}`. a2a.proto defines SendMessageResponse and StreamResponse as oneofs (the message field is JSON-named "message"). A consumer that follows the proto or prose shape will find no `task` key on a bare Task and fail to parse. This is a deliberate design choice (DESIGN.md:22, and the repo digest section 2 says bare), so the real risk is spec ambiguity, not a coding slip. The probe confirmed bare shapes with kind discriminators.

- [A2A/medium] app.py only registers handlers for HTTPException and RequestValidationError (app.py:865-889). An unexpected exception raised inside any a2a.py handler (for example a task-store failure in tasks_list) returns Starlette's `text/plain` body "Internal Server Error" with HTTP 500, not the A2A envelope `{"error":{"code":-32603,...}}`. I reproduced this by making list_tasks_for_identity raise: the status was 500 and content-type was text/plain. A client that parses `response.json()["error"]` on this surface will crash on exactly the failures where it needs structure. Only the -32006 serialization path is wrapped (a2a.py:571-591).

- [A2A/medium] _config_error (a2a.py:429-434) intersects configuration.acceptedOutputModes with a fixed set using exact string equality. Probe results: ["*/*"] gives 415 / -32005, and ["Text/Plain"] gives 415 / -32005. MIME types are case-insensitive, and */* or text/* is the usual way a client says it accepts anything. Such a client is told its request is unsupported even though the agent can answer in text/plain. The set also holds the non-MIME token "text".

- [A2A/low] _parse_send (a2a.py:442-444) compares the media type to "application/json" without lower-casing. Probe: `Application/JSON` gives 415 / -32005. RFC 9110 says media types are case-insensitive. This is rare in practice but is a false rejection.

- [A2A/low] message_send applies historyLength only when it creates a new task (a2a.py:697-700). The resume branch returns `_task_wire(record)` with no length (a2a.py:662), and the message:stream snapshot always carries full history (a2a.py:880). A client that sets historyLength=0 gets full history back on a resume.

- [A2A/low] Wrong HTTP verb on a defined path returns HTTP 405 with code -32004 (probe: GET /v1/message:send). The table in models/errors.py maps -32004 to 501, and tasks_get returns 501 for the same kind of mistake (a2a.py:1090-1095). The mapping is in app.py `_A2A_CODE`, which a2a.py routes inherit. The same code therefore carries two HTTP statuses on one surface.

- [A2A/low] Message.role allows both values, and _parse_send never checks that a message/send or message/stream request carries role "user" (a2a.py:454-470). Probe: a role="agent" message created a task and was stored in task history as an agent turn, although it was fed to the model as a user turn (a2a.py:526). This pollutes tasks/get history, and context replay can show client text as agent output.

- [A2A/low] TaskStatus.error (a WireError) appears on every failed task and in the stream tail (models/a2a.py TaskStatus; a2a.py:896-901), whether or not the client asked for the task-error extension in X-A2A-Extensions. The extension is declared on the card, but the activation rule that this file applies to other extensions (RT-B-203) is not applied here. Strict consumers with additionalProperties=false on TaskStatus would reject it.
