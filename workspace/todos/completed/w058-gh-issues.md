- [ ] `GH-202` GET /admin/api/keys blocks the event loop with one synchronous table read per key ‖ group:G1
  - Creates: (modifies `agent_sdk/credentials/store.py` (new non-abstract `CredentialStore.list_items`), `agent_sdk/credentials/azure_table.py`, `agent_sdk/credentials/encrypted_sqlite.py`, `agent_sdk/auth/api_keys.py` (`count`, `list_keys`, `revoke`, `verify`), `agent_sdk/auth/middleware.py` (`_resolve_identity`), `agent_sdk/routes/admin.py` (`list_keys` route ~line 300, `revoke` route ~line 323, overview `count()` ~line 413), `agent_sdk/routes/oauth.py` (`api_keys.verify` at ~lines 917 and 1066), new `tests/test_gh202_api_key_store_off_loop.py`, new `tests/test_gh202_api_key_races.py` (race tests), `tests/test_gh183_184_service_key_mint_step.py` (`_MemStore` now subclasses `CredentialStore` so it gets `list_items`; stores passed to `ApiKeyStore` must subclass `CredentialStore` or provide `list_items`), `DESIGN.md` §6 (API keys) and the §credentials store interface section, `CHANGELOG.md`)
  - Reads: `agent_sdk/credentials/store.py`, `agent_sdk/credentials/azure_table.py` (`_UNCACHED_NAMESPACES`, `list_fields`, `get`), `agent_sdk/credentials/encrypted_sqlite.py` (`_lock`, `_decrypt`), `tests/test_audit_regressions.py` (`CountingStore`), `tests/test_forwarding.py` (`DictStore`), `agent_sdk/contrib/scheduler.py` (existing `asyncio.to_thread` use)
  - Severity: high
  - Root cause: `ApiKeyStore.list_keys()` calls `list_fields(NS_API_KEYS)` and then one `store.get` per key. On `AzureTableCredentialStore` each `get` is a synchronous HTTP round trip, and the `async def` admin route calls it directly on the event loop, so with ~56,000 keys a single-replica agent stopped answering every route (including `/health`) for ~8 minutes. `count()` and `revoke()`'s last-admin scan have the same shape. `verify()` does a synchronous `get` + `set` (`last_used`) on the loop for every API-key-authenticated request.
  - Ruling: Checkable reference: https://github.com/wailuen/a2a-sdk/issues/202#issuecomment-6259246006 (single query + off-loop for list/count/revoke; NO pagination, response shape unchanged; verify off-loop with `last_used` written only when the stored value is more than 60 s old)
  - AC: Add a non-abstract `CredentialStore.list_items(namespace) -> dict[str, str]` returning `{field: plaintext}` for every field in the namespace. The base-class default is `{f: v for f in list_fields(ns) if (v := get(ns, f)) is not None}` so third-party subclasses (e.g. `CountingStore`, `DictStore` in tests) keep working unchanged. Adding it must not make any existing subclass abstract.
  - AC: `AzureTableCredentialStore.list_items` does ONE `query_entities` on the partition and decrypts each entity's `Value` in place (same AAD `namespace`/`RowKey` as `get`), skipping `__`-prefixed RowKeys exactly as `list_fields` does and returning `{}` for `__meta__`. It does not read or populate the 5-min cache for `_UNCACHED_NAMESPACES` (API keys must stay uncached). `EncryptedSqliteStore.list_items` does one `SELECT field, value ... WHERE namespace=?` under `self._lock`.
  - AC: `ApiKeyStore.count()`, `list_keys()` and `revoke()`'s other-admin check each make exactly one `list_items(NS_API_KEYS)` call and zero per-key `get` calls (proved by a counting store in tests). `list_keys()` output (fields, values, the route's sort by `created_at` and `count`) is unchanged.
  - AC: The admin routes run `list_keys()`, `revoke()` and the overview `count()` via `await asyncio.to_thread(...)`. `revoke()`'s `AgentError` still maps to the same HTTP status and body as before.
  - AC: `verify()` is run via `await asyncio.to_thread(runtime.api_keys.verify, token)` in `middleware._resolve_identity` and at both `oauth.py` call sites. The public sync `resolve_identity()` (exported from `agent_sdk.auth`) keeps its sync signature; its docstring says it does blocking store I/O and async callers should use `asyncio.to_thread`. Do not change `runtime.oauth.verify` in this wave.
  - AC: `verify()` writes `last_used` only when the stored `last_used` is `None` or more than 60 seconds older than now (module constant, e.g. `_LAST_USED_WRITE_INTERVAL = 60.0`). A matching key whose `last_used` is fresher does no `set`. Hash comparison stays `hmac.compare_digest`; behavior for unknown/invalid keys is unchanged.
  - AC: Tests (new `tests/test_gh202_api_key_store_off_loop.py`): `list_items` on both built-in stores (sqlite directly; Azure via a fake `TableClient` that counts `query_entities` / `get_entity` calls and asserts 1 / 0, AAD-correct decrypt, `__` rows skipped, no cache entries added for `__api_keys__`); base-class default works on a minimal subclass that only implements the 5 abstract methods; `count`/`list_keys`/`revoke` do zero per-key gets; `verify` throttle (first use writes, second within 60 s does not, after 60 s writes again, via a patched clock); an event-loop-not-blocked test: with a store whose `list_items`/`get` sleeps (e.g. 0.5 s via `time.sleep`), a concurrent `GET /health` during `GET /admin/api/keys` returns well before the listing finishes; the last-admin-key refusal still works.
  - AC: Docs: `DESIGN.md` §6 notes `last_used` is accurate to ~60 s and key-store calls run off the event loop; the credential-store interface section lists `list_items` with its default. CHANGELOG `[Unreleased]` Fixed entry citing GH-202 and the ruling URL. Do NOT edit `template/`.
  - GH: https://github.com/wailuen/a2a-sdk/issues/202
  - SI: SI-2, SI-5  # Touches API-key verification and the encrypted credential store. Keys stay hashed at rest and uncached across replicas; no plaintext key, hash, or decrypted record may appear in logs, errors or responses; revocation must still take effect immediately on all replicas.
  - SI: SI-5  # Moving verify() and revoke() into asyncio.to_thread removes the atomicity they had in a single replica, and no AC covers the races this opens. Today both run as sync code on the event loop with no await inside, so in one process they cannot interleave. Race (a), a revoked key comes back: verify() does a get, then revoke() deletes the row in another thread, then verify() does its last_used set(NS_API_KEYS, key_id, json.dumps(record)). That set re-creates the full record, hash included (agent_sdk/auth/api_keys.py verify), so the revoked key works again. Race (b), admin lockout: two concurrent DELETE /admin/api/keys/{id} calls on the last two admin keys both pass the other-admin check in revoke(), then both delete, which breaks the 'last-admin revocation is refused' rule in the api_keys.py module docstring and DESIGN.md §6. Add an AC: ApiKeyStore holds one threading.Lock around revoke() (check plus delete) and around verify()'s re-read-then-write of last_used, and the last_used write must never re-create a missing row (re-read under the lock and skip the write when the row is gone). Add tests that force each interleaving (patch store.get/delete to block on a threading.Event) and assert that a revoked key stays revoked and that only one of two concurrent last-admin revokes succeeds. The 60 s write throttle makes race (a) less likely but does not close it. The same races across replicas already exist; note that in DESIGN.md §6 and leave it out of scope.
