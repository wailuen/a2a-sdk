- [x] `GH-122` oauth/authorize: CSP form-action 'self' blocks redirect to external redirect_uri ‖ group:G
  - Creates: (modifies `agent_sdk/routes/oauth.py`, `tests/test_oauth_flow.py`)
  - Reads: `agent_sdk/routes/oauth.py` (lines 55-67 `_CONSENT_SECURITY_HEADERS`, 150-163 `_valid_redirect_uri`, 266-287 `_error_redirect`/`_error_page`, 349-399 consent page render, 435-484 `oauth_authorize_approve`)
  - Severity: critical
  - Root cause: `_CONSENT_SECURITY_HEADERS` sets a static `form-action 'self'` on every `/oauth/authorize` response, including the two responses that issue a redirect to the OAuth client's external `redirect_uri` (the success 303 and the validated-redirect_uri error path). Chromium/Electron enforces `form-action` on redirect *destinations*, not just the initial submit target (crbug.com/932518), so the browser blocks the redirect and the Approve button appears to do nothing. This breaks all OAuth-based MCP connections from Claude Desktop and any Chromium-based client.
  - AC:
    - **RT-001 supersession (landed, do not revert):** an in-wave redteam finding overrode the original scope below — `form-action` is widened to include the validated `redirect_uri`'s origin on EVERY response that either hosts the form-submission redirect chain or redirects along it: `_consent_page` (the GET render, which is the document that actually owns the `<form>` the user submits) INCLUDING its 401 bad-api-key re-render in `oauth_authorize_approve`, `_error_redirect`, and the success `RedirectResponse` in `oauth_authorize_approve`. Rationale: Chromium/Electron enforces `form-action` against the form-*owning document*, not the CSP delivered on a later 30x hop (crbug.com/932518) — a bare `form-action 'self'` on the consent-page render alone still blocks the redirect even after the 30x responses were widened, so scoping the fix to only the two redirect responses (the original AC below) is insufficient and was corrected in-wave. `_error_page` (unknown client / unregistered redirect_uri — no trusted destination) is the only response that stays on bare `form-action 'self'`. Implemented as the shared `_redirect_security_headers(redirect_uri)` helper, called from `_consent_page`, `_error_redirect`, and the success redirect.
    - ~~Original AC (superseded by RT-001 above): `form-action` widened ONLY on the two responses that actually redirect there: `_error_redirect` and the success `RedirectResponse` in `oauth_authorize_approve`. Do not touch `_error_page` ... or the plain consent-page render, which stay on bare `form-action 'self'`.~~ — kept for history; the landed code and tests implement the RT-001 line above instead.
    - Do NOT implement the issue's literal "fetch() + read Location header" proposal — a `redirect:'manual'` fetch returns an opaque-redirect response with headers inaccessible to JS, and `redirect:'follow'` attempts the cross-origin navigation itself and typically fails on CORS. The dynamic form-action-origin widening is the correct fix; this repo's oauth.py deliberately avoids scripts on this page (it collects an admin API key) and that constraint should be preserved.
    - Regression tests in `tests/test_oauth_flow.py`: (a) `test_authorize_approve_widens_form_action_to_https_redirect` — a full approve POST with a valid admin key against an `https://` redirect_uri asserts the 303's CSP header contains `form-action 'self' https://<that origin>`; (b) `test_authorize_approve_widens_form_action_to_loopback_redirect` — same for a loopback `http://127.0.0.1:<port>/callback` redirect_uri; (c) `test_authorize_error_redirect_widens_form_action` — an error-redirect case (e.g. `unsupported_response_type`) asserts the CSP header is likewise widened to the validated redirect_uri's origin; (d) `test_authorize_consent_page_widens_form_action` (RT-001) — the plain GET consent-page render also widens form-action to the validated redirect_uri's origin; (e) `test_authorize_approve_bad_api_key_rerender_widens_form_action` (RT-001) — the 401 bad-api-key re-render (same `_consent_page` call site) widens identically; (f) the unknown-client / unregistered-redirect_uri 400 `_error_page` path still emits bare `form-action 'self'`.
    - Confirm (via existing `_valid_redirect_uri` behavior or a comment/test) that non-http(s) custom URL schemes (e.g. `claude://`) are already rejected at registration/validation time, so the fix does not need scheme-source handling for that case.
    - **RT-002/RT-003 landed hardening (netloc CSP-injection + IPv6 fail-closed — landed, do not revert, operator-visible):** two further in-wave redteam findings hardened the `_redirect_security_headers`/`_valid_redirect_uri` surface beyond the RT-001 widening above. RT-002: `urlparse().hostname` does not validate against the URI authority grammar (RFC 3986 reg-name permits sub-delims like `;`), so a control-char-free redirect_uri such as `https://evil.com;frame-ancestors *;/cb` parsed with the whole string as `hostname` — splicing that into the CSP form-action would inject an extra directive. Closed by never interpolating `parsed.netloc` (or unvalidated `parsed.hostname`) into the header; the origin is instead rebuilt from a sanitized hostname (validated against the new `_HOSTNAME_RE`, oauth.py:186-189 — a restricted RFC1123-like charset with no CSP-significant characters) plus an explicitly-typed port, via the new `_validated_origin(parsed)` helper (oauth.py:192-233), which also self-enforces the https-or-loopback-http scheme contract and fails closed to the bare `form-action 'self'` rather than emit an unvalidated origin. RT-003: `_HOSTNAME_RE`'s charset excludes `:`, so IPv6-literal redirect_uris (e.g. `https://[2001:db8::1]/cb`) fail `_validated_origin` reconstruction (no bracket-aware re-emission exists) and are now REJECTED OUTRIGHT by `_valid_redirect_uri` rather than silently widened into a malformed CSP origin — fail-closed over emitting a broken header. **This is a real, operator-visible narrowing of `_valid_redirect_uri`, enforced at BOTH `/oauth/register` DCR registration and `_validate_authorize`'s authorize-time re-validation (oauth.py:444):** an IPv6-literal or non-RFC1123-charset redirect_uri that would have been accepted before this wave is now rejected at both surfaces. Not expected to affect real registrations (OAuth clients targeting this endpoint use hostnames or loopback), but is intentional, not incidental — do not "fix" by loosening `_HOSTNAME_RE`'s charset alone without also adding bracket-aware IPv6 origin reconstruction. Regression tests: `test_valid_redirect_uri_rejects_csp_significant_netloc`, `test_dcr_rejects_csp_injection_redirect_uri`, `test_redirect_security_headers_never_reflects_raw_netloc`, `test_redirect_security_headers_rejects_space_injected_netloc`, `test_validated_origin_enforces_scheme_at_boundary` (RT-002); `test_valid_redirect_uri_rejects_ipv6_literal`, `test_validated_origin_rejects_ipv6_literal`, `test_dcr_rejects_ipv6_literal_redirect_uri` (RT-003) — all in `tests/test_oauth_flow.py`.

Correction (RT-001 audit-trail fix, LRN-124): this line originally claimed the landed fix reflects a client-controlled redirect_uri origin (f"{parsed.scheme}://{parsed.netloc}") into the CSP form-action header — that is NOT what shipped and must not be read as a description of the code. The landed fix deliberately does the opposite: it never interpolates parsed.netloc; the origin is reconstructed from a sanitized hostname (_HOSTNAME_RE) plus an explicitly-typed port via the new _validated_origin helper (oauth.py:186-233) — see the RT-002/RT-003 AC bullet above for the full mechanism and the resulting redirect_uri-acceptance narrowing. _valid_redirect_uri's control-char/length guard (oauth.py:239-240) remains in force ahead of this as defense in depth.
