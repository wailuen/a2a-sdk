## G1 — MCP elicitation for ToolInterrupt

- [ ] `GH-224` protocol/mcp: MCP elicitation for ToolInterrupt ‖ group:G1
  - Creates: `agent_sdk/routes/mcp_elicitation.py` (new: schema converter, pending-request table, outcome mapping), `tests/test_gh224_mcp_elicitation.py` (new)
  - Modifies: `agent_sdk/routes/mcp.py` (session capability tracking at `initialize`, SSE answer mode for `tools/call`, routing of client JSON-RPC responses, `ToolInterrupt` branch ~line 899, session delete/eviction cleanup), `agent_sdk/config.py` (new `mcp_elicitation_timeout_seconds` setting, env `AGENT_SDK_MCP_ELICITATION_TIMEOUT_SECONDS`, default 300, positive), `docs/protocols.md` (MCP section: elicitation), `docs/tools.md` (ToolInterrupt over MCP), `workspace/components/README.md` (new C-NNN row for the converter/pending table), `CHANGELOG.md`
  - Reads: `agent_sdk/agent/loop.py` (`ToolInterrupt`, line ~163), `agent_sdk/contrib/action_gate/gate.py` (the interrupt it raises and its `resume_handler`), `agent_sdk/routes/a2a.py` and `docs/protocols.md` (how A2A/AG-UI resume folds a value back, to mirror it), `tests/test_gh204*` and every existing `tests/test_*mcp*` file (must stay green unchanged — non-elicitation sessions keep today's bytes)
  - Depends: (none)
  - Severity: low (feature; issue severity)
  - Root cause: MCP `tools/call` has no way to ask the user a question mid-call, so a `ToolInterrupt` always ends the call with a fixed `isError` (mcp.py ~899-911), even when the client declared the `elicitation` capability and could show the question to the user.
  - AC (trigger): elicitation is used only when the session's `initialize` params declared `capabilities.elicitation` (an empty object `{}` counts as form mode; a declaration with only `url` and no `form` does not count) AND the negotiated version is 2025-06-18 or newer AND the `POST /mcp` `Accept` header includes `text/event-stream`. The capability is stored with the session at `initialize` (the session record in `_sessions`), never re-read from a later request. In every other case the reply is today's JSON-mode `isError`, byte-for-byte (existing tests unchanged prove it).
  - AC (transport): when the trigger holds, `tools/call` is answered as `text/event-stream` (the Streamable HTTP SSE response mode). The stream carries, in order, zero or one `elicitation/create` JSON-RPC request and then exactly one JSON-RPC response for the `tools/call` id, after which the stream ends. Calls that never interrupt still get a correct single-response stream. Response headers keep `Mcp-Session-Id` / `MCP-Protocol-Version` as the JSON mode does. The stream counts against the existing per-identity stream admission budget (`_get_streams` / `SlotTable`); when the budget is full the call falls back to today's JSON-mode reply, never a 5xx. Legacy SSE (`/mcp/sse` + `/mcp/messages`) is unchanged.
  - AC (request): `elicitation/create` params are `{"message": <tool message, sanitized with safe_line_text and capped like today's interrupt text>, "requestedSchema": <converted schema>}`; for a 2025-11-25 session add `"mode": "form"`. The request id is server-generated, unguessable (`secrets.token_urlsafe`), and unique per session. Never put `interrupt.reason` or any argument value in the request.
  - AC (schema converter): `response_schema` (JSON Schema) converts to MCP's flat `requestedSchema`: `type: "object"` with top-level `properties` only, each one of `string` (with optional `minLength`/`maxLength`/`format` in email|uri|date|date-time), `number`/`integer` (optional `minimum`/`maximum`), `boolean` (optional `default`), or a string `enum` (optional `enumNames`); `title`/`description` kept; `required` kept when every listed name is a kept property. Anything else — nested objects, arrays, `$ref`, `anyOf`/`oneOf` that is not a plain nullable primitive, `additionalProperties: true` — makes the converter return "not convertible". A property whose name matches the SDK's existing secret-like name check (reuse the existing helper; do not write a new pattern list) also makes it "not convertible". A `None` `response_schema` converts to an empty object schema (`{"type": "object", "properties": {}}`) so a plain "approve?" interrupt still elicits. "Not convertible" → today's `isError`, and a log line naming the tool only.
  - AC (pending table): server requests are tracked per session in a table keyed by request id, holding the identity, session id and an `asyncio.Future`. A client JSON-RPC response (`_is_jsonrpc_response`, mcp.py ~1090) arriving on `POST /mcp` resolves the matching entry only when id, session id and identity all match; otherwise it is ignored with 202 and a log line without any value. A second response for the same id is ignored. Per-session cap: at most 8 pending entries (a fixed module constant); over the cap the call falls back to today's `isError`. Entries are removed on resolve, on timeout, when the stream's client disconnects, and on session `DELETE` or LRU eviction (the waiting call then ends with the cancel `isError`).
  - AC (outcome): `action: "accept"` → validate `content` against the converted schema (types and `required` only; on failure return a fixed `isError`, no echo), then call `interrupt.resume_handler(content)` when set and build the tool result from its return through the same path a normal tool return takes (`_tool_text` / structuredContent rules); with no `resume_handler`, return the accepted `content` as JSON text, capped. `action: "decline"` or `"cancel"`, or an `error` response → fixed `isError` text (one per case, constants beside `MCP_INTERRUPT_SUFFIX`), never echoing user input. A `resume_handler` that raises goes through the same `except` branches a tool error takes today (AgentError, TimeoutError, generic). A `resume_handler` that raises `ToolInterrupt` again ends with today's interrupt `isError` (no second elicitation in the same call).
  - AC (timeout): the wait for the answer uses `settings.mcp_elicitation_timeout_seconds` (default 300) and does not consume the tool's own timeout. On expiry the pending entry is removed and the call returns a fixed "no answer received" `isError`. The `resume_handler` call after accept runs under the tool's normal timeout (`resolve_tool_timeout`).
  - AC (action_gate): an action_gate approval interrupt elicits like any other (ruling item 6); a test proves the gated action runs only after `accept` and never after `decline`, `cancel` or timeout.
  - AC (capability advertisement): no server capability is added for elicitation (it is a client capability); `initialize` output is unchanged.
  - AC (docs): `docs/protocols.md` MCP section describes when elicitation is used (the three trigger conditions), the SSE answer mode, the outcomes, the timeout setting, the 8-pending cap, and that Claude.ai web does not declare elicitation so it keeps the `isError` reply. `docs/tools.md` explains that `response_schema` must be flat primitives to elicit over MCP, that secret-like fields never elicit, and the fallback.
  - Tests: `tests/test_gh224_mcp_elicitation.py`. The test must drive the stream and the answering POST concurrently; `httpx.ASGITransport` buffers whole responses, so drive the ASGI app directly (a small receive/send harness) or run a real uvicorn server on a free port — do not mark tests skip. Cases: (1) elicitation-capable session + interrupting tool: stream gives `elicitation/create` with the converted schema, client POSTs `accept`, stream ends with the `resume_handler` result; (2) no `resume_handler`: result is the accepted content; (3) `decline`, (4) `cancel`, (5) timeout (set the setting low): fixed `isError`s, input not echoed; (6) session without the capability, (7) 2025-03-26 session, (8) `Accept` without `text/event-stream`: today's JSON `isError` byte-for-byte; (9) non-convertible schema (nested object) and (10) secret-like field name: today's `isError`; (11) response from another session, another identity, unknown id, duplicate id: ignored, call still waiting; (12) session DELETE while waiting ends the call with the cancel `isError` and clears the entry; (13) action_gate: action runs only on accept; (14) 2025-11-25 session gets `mode: "form"`, 2025-06-18 does not; (15) a non-interrupting tool from an elicitation-capable session gets a valid single-response stream; (16) `accept` with content failing the schema returns the fixed `isError`. Each test must fail when its behaviour is removed (LRN-560).

  - SI: SI-2  # Elicitation messages, isError texts and logs never carry the rejected input, accepted content values, interrupt.reason text beyond today's sanitized log, or argument values. The request id is the only correlation value in logs.
  - SI: identity binding  # A pending entry resolves only for the same identity AND the same session that received the request; cross-session or cross-identity answers are ignored (test 11). No credential is ever requested through elicitation (secret-like field names are refused).
