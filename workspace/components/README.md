## Descriptions

**C-001 crypto** (`agent_sdk/credentials/crypto.py`)
Shared AES-256-GCM encryption module extracted from EncryptedSqliteStore. Exports `derive_key`, `encrypt`, `decrypt`, and `PBKDF2_ITERATIONS`. Reusable by any backend that needs authenticated symmetric encryption with namespace/field AAD binding.

**C-002 CommitmentBackend** (`agent_sdk/contrib/commitments/backend.py`)
Abstract base class extracted from CommitmentStore. Defines the public contract (`add`, `claim_due`, `mark_fired`, `mark_failed`, `cancel`, `reap_stale_firing`, `get`, `list`, `close`) so Azure Table Storage and any future durable-store implementations can be swapped without touching CommitmentExecutor or CommitmentsSource.

**C-003 SubscriptionBackend** (`agent_sdk/contrib/webhooks/backend.py`)
Abstract base class extracted from SubscriptionStore. Defines the public contract (`initialize`, `upsert`, `set_expiration`, `delete`, `get`, `list`, `due_for_renewal`, `close`) so GraphSubscriptionManager and webhooks_renewal_lifespan can accept any backing store (SQLite, Azure Tables, in-memory) via dependency injection.

**C-005 TaskStore** (`agent_sdk/tasks/store.py`)
Abstract base class for the SDK's task lifecycle store. Defines the public contract that `InMemoryTaskStore` (`agent_sdk/tasks/memory.py`) implements and that external durable-store implementations (e.g. AzureTableTaskStore) must satisfy. Key public methods: `create`, `get`, `subscribe`, `unsubscribe`, `find_interrupt`, `publish`, `close_streams`, `mark_interrupted`, `deliver_resume`, `interrupt_ttl_remaining`, `persist_messages`, `persist_status`, `evict`, `sweep`, `close_all`, `context_messages`, and `context_reusable_messages`. `persist_every_status` (RT-007, bool, default `False`) is a public class attribute, not a method — a subclass sets it `True` to opt into receiving `persist_status` on every transition (including the repeated WORKING ones) instead of only `TERMINAL_STATES`/`INTERRUPT_STATES`. Breaking change in w022: `list_tasks_for_identity` return type changed from `tuple[list[Task], str | None]` to `tuple[list[Task], str | None, int]` — the third element is the total count of all matching tasks regardless of cursor position. External `TaskStore` subclass implementors must update their `list_tasks_for_identity` signature to match. w031/AGUI-1 (RT-002, non-breaking): added `interrupt_ttl_remaining(task_id) -> float | None`, a relative-seconds-to-expiry hook the AG-UI route now reads instead of the old absolute `record.interrupt_deadline` when serializing `Interrupt.expiresAt`. The base-class default returns `None` (unknown) so pre-existing external `TaskStore` subclasses keep instantiating without an override — but they will silently stop emitting `expiresAt` on AG-UI interrupt outcomes (previously an absolute, monotonic-clock-derived `int` was emitted; now nothing is, rather than a wrong value). External subclassers who want `expiresAt` back must override `interrupt_ttl_remaining` to compute seconds-remaining from their own store's tracked deadline and clock. Call this out explicitly in the 0.5.40 CHANGELOG entry under "Breaking/behavior changes for TaskStore subclassers". w039 GH-150 follow-up (RT-005, non-breaking): added `persist_messages(record: TaskRecord) -> None`, the write hook for out-of-loop `record.messages` repairs — `agent/runner.py`'s `repair_dangling_tool_use` (called from `routes/a2a.py`'s `tasks_cancel` and from `runner.py`'s deferred background awaiter and terminal exception handlers) mutates `record.messages` directly on the `TaskRecord` object `get()` returned, with no separate write call; `InMemoryTaskStore`'s `get()` already hands back the live object by reference so it needs no override. (The same repair also clears `record.pending_tool_results`, but that field is runtime-only turn state — never serialised, per its own field comment in `tasks/store.py` — and is NOT part of this hook's flush contract.) The base-class default is a no-op (same precedent as `interrupt_ttl_remaining`), so a pre-existing external `TaskStore` subclass keeps instantiating without one — but a `get()` that deserializes a fresh copy per call (the `AzureTableTaskStore` shape this ABC exists for) will then silently keep dropping every such repair, leaving a malformed toolUse-without-toolResult transcript in durable storage for `context_messages()` to replay. External subclassers whose `get()` is not a live-reference passthrough MUST override `persist_messages` to flush the record's `messages` back to storage keyed by `record.task.id`. `repair_dangling_tool_use` takes the record itself, not a bare `task_id`, precisely so a copy-on-`get()` store can persist the exact object the caller mutated. Call this out explicitly in the next CHANGELOG entry under "Note for TaskStore subclassers". RT-B-003 follow-up (non-breaking): `persist_messages` alone is NOT sufficient for durability — `tasks_cancel` also mutates `record.task.status` on the same `TaskRecord`, and a store that overrides only `persist_messages` never observes the `CANCELED` transition, so `context_messages()`'s `TERMINAL_STATES` filter never finds the task and the repair `persist_messages` just flushed is never read back either. Added `persist_status(record: TaskRecord) -> None` (same non-abstract, default-no-op shape). RT-007 (debug round 4) superseded this entry's original claim that `persist_status` was "wired into `tasks_cancel` right after the `CANCELED` assignment": `tasks_cancel` no longer mutates `record.task.status` or calls `persist_status`/`persist_messages` itself at all (`agent_sdk/routes/a2a.py`, RT-001/RT-004) — it now calls `agent_sdk/agent/runner.py`'s `set_task_status` (C-019) for the CANCELED transition, the same choke point every other terminal/interrupt transition (COMPLETED, FAILED, AUTH_REQUIRED, INPUT_REQUIRED) already goes through. **`set_task_status` is the SDK's ONLY caller of both `persist_messages` and `persist_status`** — see C-019's contract for the fail-closed ordering (`persist_messages` first, `persist_status` only if that flush succeeded) and the `TERMINAL_STATES`/`INTERRUPT_STATES` flush condition `persist_every_status` opts out of by default. A durable subclasser needing continuation to survive cancellation must still override BOTH `persist_messages` and `persist_status` — only the caller moved, not the requirement.

**C-007 sanitize_text (also exported as `safe_error_text`)** (`agent_sdk/common/redact.py`)
LANDED. `sanitize_text(s, *, max_len=64)` — the single definition of the truncate + control-char-strip contract for untrusted (model-/caller-/tool-supplied) strings reaching a log line or the wire (SI-2). The character class is C0 (`0x00-0x1F`) + DEL (`0x7F`) + C1 (`0x80-0x9F`), each mapped to a space; C1 is deliberately included (NEL `0x85` is a line break to many log/terminal consumers, CSI `0x9B` is a single-byte ANSI escape introducer), so a narrower `range(0x20)`-only copy would NOT satisfy this contract.

Call sites, all routed through the one helper — do not re-inline a `translate(dict.fromkeys(...))` map anywhere else:
- `agent_sdk/agent/loop.py` — unknown-skill and unknown-tool branches, on the model-supplied name (`sanitize_text(requested_name)` / `sanitize_text(tc.name)`). This module previously carried a byte-identical private copy (`_CONTROL_CHAR_MAP` + `_sanitize_model_name`, including the comment block); it was DELETED when the shared helper landed. The prior version of this entry still read "the pattern is currently inline at loop.py" and "the existing redact.py only masks secret-named keys/bearer values, not control chars" — both were false once the helper landed, and leaving them here is what invites a third divergent copy.
- `agent_sdk/models/content_types.py` — `ContentModel._metadata_suffix()`, on each rendered `metadata` key and value (`max_len=_METADATA_SUFFIX_FIELD_MAX_LEN`), before the GH-63 disclosure envelope reaches the mandatory A2A/MCP text fallback (RT-A06).

Note the sibling helpers in the same module cover different threats and are not substitutes: `redact()` masks secret-NAMED dict keys, `redact_value()` masks bearer values. Neither strips control characters.

**C-007 `safe_id_text(value, *, max_len=256)`** (`agent_sdk/common/redact.py`, GH-156) -- id-preserving sibling for identifiers a model copies back into a tool call. Strips control chars, caps length, whitespace -> `_`, neutralises only `()[]<>|`; keeps `= + / : , . _ - ! ~ @` byte-exact. Use for ids; use `safe_cell_text` for display cells.

**RT-003 (origin/main fork reconciliation):** this SDK's `origin/main` lineage diverged onto the same C-007 contract under the name `safe_error_text(value, *, max_len=64)`, plus three functions this lineage had none of at all — `frame_locations` (traceback `file:line` formatter for diagnostic logs), `safe_cell_text` (GH-130 structural-separator neutralisation for delimited single-line renders), and `safe_block_text` (the multi-line-markdown counterpart, `\n`/`\t` preserved as content). Reconciled rather than left to break a future merge: `sanitize_text` stays canonical (matches this lineage's own call sites above); `safe_error_text = sanitize_text` is now a deprecated alias — same function object, not a second copy — so an upstream-authored `from ..common.redact import safe_error_text` resolves instead of raising `ImportError`. `frame_locations`/`safe_cell_text`/`safe_block_text` are ported verbatim into `agent_sdk/common/redact.py`, self-contained, with their own `_CONTROL_CHARS`/`_BLOCK_CONTROL_CHARS` constants (a wider span than `sanitize_text`'s — includes U+2028/U+2029 — scoped to these three, so `sanitize_text`'s existing contract for its own callers is untouched). None of the three are wired into any local call site yet (that is `origin/main`'s GH-130/LRN-044 work, still ahead of this lineage, e.g. `ContentModel.to_plain_text()` delimiter safety and the dispatch catch-all `frame_locations` logging) — they exist here purely so the symbols are defined and merge-compatible. See `tests/test_rt003_redact_c007_upstream_reconciliation.py`.

**Still open, NOT part of this reconciliation:** the same GH-135/RT-004 "unknown tool input" fix forked independently in `agent/loop.py`'s `ToolInputValidationError` branches — this lineage's `ToolInputValidationError` carries `tool_name`/`input_model` on the exception itself (read as `exc.tool_name`/`exc.input_model` at 5 call sites: `agent/loop.py` x2-3, `routes/mcp.py`, `routes/admin.py`), while `origin/main`'s carries only `tool_name` and reads `input_model` from the caller's own `entry.decl.input_model` closure variable instead. **C-010 ToolEntry.invoke_any** (`agent_sdk/agent/registry.py`)
Shared is_generator/DeferredResult tool-dispatch helper (RT-001, follow-up to RT-002/LRN-116). `invoke_any(arguments, adapters, *, timeout=None, policies=None)` drains a coroutine or async-generator tool without the caller having to branch on `decl.is_generator`, and resolves a returned `DeferredResult` inline for callers with no background delivery channel. When `timeout` is given, it bounds the initial invoke/drain (`asyncio.wait_for`/`asyncio.timeout`, mirroring every other invocation surface) AND the DeferredResult handle under the SAME single deadline — the handle gets only the remaining budget, never a fresh `timeout` seconds on top (RT-003: previously `agent_sdk/routes/mcp.py` applied the full timeout twice sequentially). When `timeout` is omitted (the commitments executor's call shape — no per-call deadline of its own), the initial invoke/drain stays unbounded and only the DeferredResult handle is bounded, via `resolve_tool_timeout` against `policies` (or a default `LoopPolicies()`). Only the executor's CALL SITE is legacy/unchanged; the BEHAVIOR is not — RT-001: before GH-120 `invoke_any` returned the `DeferredResult` verbatim and `executor.py` dropped the handle unawaited (side effect never ran, yet the commitment was still marked fired). The handle is now awaited on this timeout-free path too, so a committed `long_running` tool is marked fired only after its deferred side effect completes (and failed if it times out) — proven end-to-end by `tests/test_rt002_invoke_any_deferred_result.py::test_executor_fire_actually_runs_deferred_handle` (real ToolEntry through the real CommitmentExecutor). `agent_sdk/routes/mcp.py`'s `_handle_tools_call` and `agent_sdk/routes/admin.py`'s `try_tool` both now call this (previously each re-implemented the `is_generator` branch inline, and `admin.py`'s `try_tool` didn't handle `DeferredResult` at all — silently trying to JSON-encode the raw object); `agent_sdk/contrib/commitments/executor.py` continues to call it with no `timeout`/`policies` (call site unchanged; the handle is now awaited rather than dropped). Any future error-mapping/timeout fix to tool dispatch belongs here, not in a fourth re-implementation. The nested-`DeferredResult`-resolution step itself is NOT inline here — it delegates to the separately-registered module-level helper **C-012 `resolve_deferred_result`**, which `runner.py`'s background deferred-job awaiter also calls directly (bypassing `invoke_any` entirely, since it isn't dispatching a fresh tool call). See C-012 for the cross-surface parity contract that split enforces.

**C-011 dispatch_tool (generator-aware invoke helper, planned)** (`agent_sdk/agent/registry.py`)
w033 GH-115 fixed `routes/mcp.py`'s `_handle_tools_call` by routing it through the already-extracted `ToolEntry.invoke_any()` (C-010), NOT by building a new helper — so `dispatch_tool` as described here does not exist in code yet. It remains distinct from C-010: `invoke_any` unconditionally discards interim `LoopEvent`/`ToolProgressEvent` items when draining `invoke_gen()` (by design — its callers, `routes/mcp.py` and `routes/admin.py`'s `try_tool`, have no channel to forward them), and `agent/loop.py`'s tool-dispatch branch therefore still keeps its OWN separate inline `is_generator` branch so it can forward `ToolProgressEvent` downstream to the live A2A/AG-UI stream — the exact duplication LRN-116's Prevention clause warns will recur on a future surface. Logged here as planned so the next surface or refactor that touches tool dispatch builds this instead of a third divergent copy.

**C-012 resolve_deferred_result** (`agent_sdk/agent/registry.py`)
Module-level (not `ToolEntry`-bound) nested-`DeferredResult` resolver, extracted out from under C-010 (RT-001). `resolve_deferred_result(result, *, tool_name, handle_timeout)` follows a chain of nested `DeferredResult` up to `_MAX_DEFERRED_RESOLUTIONS` deep (GH-120/GH-121), calling `handle_timeout()` fresh before each await so a caller enforcing one overall deadline (RT-003) can shrink the budget as time elapses; a resolution beyond the bound closes/cancels the handle and raises `AgentError`. It is imported and called directly by **two independent modules**: `ToolEntry.invoke_any` (C-010, same module — MCP `tools/call`, admin try-tool, commitments executor) and `agent_sdk/agent/runner.py`'s `_run_deferred_background` (the A2A/AG-UI background awaiter for a `DeferredEvent`). This is the RT-001 transport-parity guarantee itself, scoped to nesting DEPTH: a nesting depth that succeeds resolving a `long_running` tool's result on one dispatch surface must succeed identically on every other, and the same holds for the point at which nesting is rejected as too deep. RT-002: that parity guarantee does NOT extend to the timeout budget spent resolving a chain. `runner._run_deferred_background` and a timeout-bearing `invoke_any` call both close `handle_timeout` over a single deadline computed once, so the remaining budget shrinks across nested awaits; `invoke_any`'s `timeout=None` shape (the commitments executor — its only caller with no per-call deadline of its own) instead re-derives a FULL `resolve_tool_timeout` budget before every nested await. A slow nested-`DeferredResult` chain can therefore succeed on the commitments surface while timing out on MCP/A2A for the identical tool contract — an intentional consequence of the commitments path having no deadline to shrink, not a drift bug. A future change wanting timeout-budget parity to match depth parity would need to thread a shared deadline through `CommitmentExecutor._fire` (e.g. a configurable per-fire timeout passed as `invoke_any(..., timeout=...)`), not a change to this helper. **C-019 set_task_status** (`agent_sdk/agent/runner.py`)
RT-005 registration (debug round 4): promoted from the module-private `_set_status` into a public cross-module choke point imported by `agent_sdk/routes/a2a.py`, with its own non-obvious contract — but it had no C-NNN row of its own, only prose inside C-018's entry, so a future writer of a terminal transition had no registry row to find. It is the single choke point for EVERY in-place `record.task.status` mutation the SDK makes (WORKING, COMPLETED, FAILED, CANCELED, AUTH_REQUIRED, INPUT_REQUIRED) across `run_task_worker`, `_run_deferred_background`, and `routes/a2a.py`'s `tasks_cancel`.

Contract, in the order it matters:

1. **The in-memory status mutation always commits.** It is never rolled back to compensate for a durable-write failure — the caller's wire response has already committed to it (RT-001). A route must never roll back a terminal state it has already returned and published.
2. **`repaired` gate.** `repaired=False` (threaded from `repair_dangling_tool_use_safe`) means `record.messages` is NOT safe to persist, and skips both durable flushes entirely. It must never be used to report a failed durable *write* — only a failed in-memory repair (RT-001, debug round 4): a write failure is already handled correctly by the `flushed` gate below, and routing it through `repaired` instead made a transient blip skip the very path designed for it, permanently stranding the durable record non-terminal.
3. **Flush condition.** `persist_messages` and `persist_status` are flushed only for `TERMINAL_STATES` and `INTERRUPT_STATES` — never for the repeated WORKING transitions, which are re-applied once per streamed chunk. Both flushes share one condition so they cannot drift apart (RT-B-104). A store wanting the old every-transition granularity opts in with `TaskStore.persist_every_status = True` (RT-007).
4. **Fail-closed ordering.** `persist_messages` runs FIRST; `persist_status` runs only if that flush actually succeeded (RT-B-007). A durably terminal task over a transcript that never arrived is exactly what `context_messages()` would later replay into Bedrock's Converse API.
5. **Single flush point.** It is the ONE `persist_messages` write per terminal transition, for repair callers as well as plain ones (RT-007, debug round 4) — `repair_dangling_tool_use_safe` takes no `store` and issues no write of its own. These hooks are plain synchronous `def`s whose durable writes block the event loop.
6. **Guarded.** A failing durable write degrades to an unpersisted status rather than raising out of a hot status-transition path (RT-B-003).

Any future terminal or interrupt transition MUST route through this function rather than assigning `record.task.status` directly — that is what `tasks_cancel` used to do, hand-rolling a divergent and fail-unsafe copy of items 1, 4 and 6.
